Part I — The manual

1What Overwatch is

A small touchscreen that sits on your desk and tells you things your computer knows but hides.

Its first page is a pair of dials showing the same numbers as Claude Code's /usage command — your 5-hour session and your 7-day week — each turning green through amber to red, with a countdown to when it resets. Codex and Claude Desktop are read the same way.

Swipe left for a music transport, right for an app launcher. Tap the gear for settings. Leave it alone and a drawn face takes over the screen.

It plugs in over USB. There is no WiFi to configure, no account to make, and no cloud service in the path: a small program on your computer reads your local usage files and pushes frames down the cable.

The two halves

HalfWhat it does
The board

The daemon
Python, on your computer		 Reads Claude Code's status line, its hooks, Codex's logs and Claude Desktop's cache; works out the numbers; sends them down the cable. Also launches apps and reads your music player when the board asks.

2What you need

2.1  The board

Either of two things works. The firmware is written for the first and has been proven on the second.

Option A — the integrated board

An ESP32-2432S028, sold everywhere as a "Cheap Yellow Display" (CYD): an ESP32 with a 2.8 inch 320×240 resistive touch panel on one PCB, about $12. Nothing to wire.

Option B — a discrete ESP32 and panel

An ESP32 DevKitC (WROOM-32) and a standalone KMRTM28028-SPI 2.8 inch module, joined by 13 jumpers. This is the combination this project actually runs on, verified 23 September 2026: screen draws, colours correct, touch lands on target, daemon connects.

The pin map is unchanged from the CYD's, so no device-tree overlay needs editing:

It would land on GPIO 12, which the ESP32 samples at reset to choose its flash voltage. The CYD's panel never drives MISO — the display is declared write-only — so the CYD gets away with wiring it. A module that does drive it stops the board booting, and the wire you were told to fit is the last thing you would suspect.

Two more traps on the same connector: the pin is T_OUT, not T_DO — both spellings exist on these modules. And the DevKitC silkscreen calls GPIO 36 and 39 VP and VN, so they are not where you will look for them.

The full recipe, including the two config files and the macOS and zsh gotchas, is in firmware/WIRED.md.

3Installing it on a computer

3.1  One command

Open a terminal and paste the line for your machine. It downloads the program, unpacks it, and runs it.

macOS — Apple Silicon

curl -fsSL https://github.com/SleepyUnicon/Overwatch/releases/latest/download/overwatch-macos-arm64.tar.gz | tar xz && ./overwatch/overwatch

macOS — Intel

curl -fsSL https://github.com/SleepyUnicon/Overwatch/releases/latest/download/overwatch-macos-x86_64.tar.gz | tar xz && ./overwatch/overwatch

Linux

curl -fsSL https://github.com/SleepyUnicon/Overwatch/releases/latest/download/overwatch-linux-x86_64.tar.gz | tar xz && ./overwatch/overwatch

Windows — PowerShell

curl.exe -fsSL -o overwatch.zip https://github.com/SleepyUnicon/Overwatch/releases/latest/download/overwatch-windows-x86_64.zip && tar -xf overwatch.zip && .\overwatch\overwatch.exe
Use the command, not a download link

macOS marks anything downloaded by a browser as quarantined and Gatekeeper refuses to run it until the app is notarised — you get "cannot be opened because the developer cannot be verified". curl sets no quarantine flag, so the line above just works. This is the reason the install is a command rather than a button.

3.2  What overwatch install does

Running the unpacked program with no arguments is the same as overwatch install. It is the only step, and it is reversible.

StepWhat changes
Copies itselfto ~/.overwatch/bin/, so you can delete the folder you downloaded
Status lineadds a statusLine entry to ~/.claude/settings.json. If you already have one it is chained, not replaced — yours still renders
Claude hooksregisters 10 events (SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Notification, Stop and others) so the board can show what each session is doing
Codex hooksthe same, in ~/.codex/hooks.json, if Codex is present
DriverWindows only — offers the CH340 USB driver
Login serviceregisters a background service that starts at login and restarts if it dies

It refuses rather than guesses. If settings.json does not parse, it changes nothing and says so — the alternative would be writing a fresh file over one you were halfway through editing.

3.3  Running at login

This is automatic, and part of install. On macOS it is a launchd LaunchAgent at ~/Library/LaunchAgents/com.overwatch.bridge.plist, with RunAtLoad and KeepAlive set, and a 10-second throttle so a repeatable crash cannot become a spin. Linux gets a systemd user unit; Windows gets a Scheduled Task with an at-logon trigger.

Login, not boot

It starts when you log in, not when the machine powers on — and that is correct rather than a shortcut. The daemon needs your user session to read ~/.claude and to hold the serial port. A boot-time daemon would start earlier and be unable to do its job.

Confirm it with overwatch status, which should say running (launchd, pid N).

4Pairing the board

Plug the board in over USB. The daemon finds it on its own — there is nothing to select.

A board that has never seen a computer shows a setup screen with a QR code and an address. This exists because of a hardware fact: the board is an ESP32 behind a USB-to-serial chip, so to a computer it is a serial port and nothing else. It cannot autorun, cannot pretend to be a keyboard and type a URL, and cannot mount a drive with a shortcut on it. Those need native USB, which this silicon does not have. So the board shows the address and a person carries it across.

4.1  From the panel

  1. Scan the QR with a phone. It opens sleepyunicon.github.io/Overwatch.
  2. The code carries a pairing token in the URL fragment, so the page opens already connected to your computer. Browsers never send a fragment to a server, so the secret reaches the page without crossing the network — GitHub never sees it.
  3. Follow the install command on the page.

The address printed under the code is deliberately shorter than what the code carries: no scheme, no token. It is the thing a person could reasonably type. Anyone typing it lands unpaired and finishes from the computer instead.

4.2  From the computer

The daemon serves a small page on the loopback address only:

http://127.0.0.1:8730

From there you can see whether the board is seen, start the service if it is stopped, and choose the launcher's tiles. The setup screen on the board steps aside by itself as soon as the daemon introduces itself.

The pages

  • Gauges — session and week as two rings, with the unit and percentage inside each and a countdown below. A status row appears only when something wants you; the clock holds it otherwise.
  • Music — what is playing on your computer, with transport controls.
  • Launcher — six tiles, each one an app. The board sends only a slot number; the computer decides what that means, so the mapping changes without reflashing.
  • Face — two eyes and a mouth, drawn rather than played, with moods that blend into one another.
  • Panels — three pages the computer fills in: your machine, the window in front, and the call you are on. See below.

The panels

Tap the title to move between them, and read the counter beside it. A sliding finger on this panel loses contact — one stroke arrives as five or six presses — so every navigation on this device has a tap path, and this is the panels' one.

Four pages whose contents come from the computer, not the firmware. The board reserves four slots and draws whatever rows and tiles arrive; it is told nothing about what they mean, and a tap goes back as a slot number and a tile number. So a new panel is a Python file on the computer — no firmware build, no release, no reflash.

  • Your machine — disk free, memory free, uptime, and on Linux the temperature and fan speed as well. Titled after the machine's own name rather than its platform, because "This Mac" on a Linux desktop is the kind of small lie that makes everything else suspect.
  • Window — which window is in front and which screen it is on, with six tiles: left half, right half, top half, bottom half, fill, and the next display along. The same set macOS offers behind its green button, on the desk instead of behind a menu. Each acts on the display the window is already on, so "Left" on a three-monitor desk means the left half of the monitor you are looking at.
  • Meeting — whether you are in a call, and whether your microphone is live. Mute toggles it, Sound silences the speakers, and Show brings the call back to the front.
  • Tools — the tools of whichever application is in FRONT, six to a page. Bring Illustrator forward and the panel becomes Illustrator; tap Pen and it selects the pen. It follows the front window rather than the launcher, so it also works after you switch with the keyboard, or for an application that was open before Overwatch was.
Mute means the system microphone

Not the meeting's own mute button. Zoho Meeting, Google Meet and half of Teams run in a browser tab, and driving their buttons would mean guessing each application's keyboard shortcut. The system microphone is one control for all of them, needs no window focus, and — the part that matters for a panel — can be read back, so the row shows what is true rather than what the last tap intended.

The trade-off: the meeting still shows you as unmuted, because as far as it knows you are. Nobody hears you, and the other participants see an open microphone icon. If you would rather drive the application's own button, bind its shortcut to a launcher tile instead.

A call is detected from the browser's open tabs on macOS and from window titles on X11. The Linux side is weaker and says so: no browser publishes its tabs to the window manager, so a call in a background tab will not be seen.

Six tiles wrap, and cost two rows

Up to four tiles sit in one row. Five or six wrap to a second row of three, because six across a 320 px screen would be 41 pixels a button — about five characters, which fits neither "Select" nor "Direct". Three across is 90 pixels and fits everything worth writing.

The second row of buttons stands where the fourth and fifth text rows would be, so a panel with more than four tiles shows three rows of text instead of five. Both halves enforce that: the computer trims the extra rows before sending them and the board declines to draw them.

The tools panel

Overwatch ships tool sets for Adobe Illustrator, Photoshop and InDesign. Any other application shows "none set" until you name it in ~/.overwatch/tools.json:

{
  "Blender": [
    {"label": "Move",   "keys": "g"},
    {"label": "Rotate", "keys": "r"},
    {"label": "Scale",  "keys": "s"}
  ]
}

Naming an application replaces its shipped set rather than adding to it, so you can remove a tile you do not want. Six is the limit; a seventh would be accepted and never drawn, so it is dropped here instead.

Why the shipped tiles only change tools

Every default is a single key that selects a tool and does nothing else. That is deliberate, and the reasoning is worth knowing before you add your own. A tool shortcut is idempotent — pressing it twice is pressing it once — and visible, because the palette changes where you can see it. Press the wrong one and the next tap undoes it.

Nothing that writes to a document has either property, and a tile is one tap away from work you have not saved. So Overwatch refuses delete, cmd+s, cmd+w, cmd+q and cmd+z even when a config file asks for them. If you want one of those on your desk, put it on a launcher keys tile, where you have had to think about it.

Sending a keystroke needs the same Accessibility permission the window panel does — see the table above, and the note in §6.2 about losing it on every update.

Launcher tiles that are not apps

The six launcher slots live in ~/.overwatch/apps.json, and a slot can be three things. The board is unchanged by any of it — it still sends a slot number and draws an icon or a label.

[
  "Terminal",
  {"keys": "cmd+shift+4", "label": "Shot"},
  {"run": ["pactl", "set-sink-mute", "@DEFAULT_SINK@", "toggle"],
   "label": "Mute", "icon": "settings"},
  "Visual Studio Code",
  "", ""
]
  • A name — the app to bring to the front. On Linux the command comes from the application's own desktop entry, not from the name run as if it were a program.
  • keys — a keystroke to send. Write cmd on either platform; on Linux it becomes Super. Needs Accessibility on macOS and xdotool on X11.
  • run — a command to start. It is not waited for, so a tile may launch something long-running.
  • icon — optional on any of them. One of claude, illustrator, photoshop, spotify, brave, chrome, vscode, terminal, obs, pcsx2, settings. An icon beats a label on the tile; an unknown name is ignored and the label is drawn instead.
run must be a list, never a string

A list is passed straight to the operating system as a program and its arguments. A string would be handed to a shell, and the difference between the two is the difference between running a program called x; rm -rf ~ and running the second half of it. A string is therefore refused outright, as is an empty list — the slot falls back to the stock grid rather than the daemon refusing to start.

The web picker on 127.0.0.1:8730 edits this file too, and keeps hand-written keys and run entries it cannot draw. An earlier version kept only the plain names, so editing any one tile silently erased every command in the file.

Themes

Light is the default. Dark is in settings. Switching rebuilds the screen rather than restyling it — LVGL keeps no back-reference from a styled object to the colour it was given, so a live switch would mean walking every object on every screen and knowing which role each colour played. Getting one wrong leaves a single unreadable label that nobody finds until a customer does.

6Keeping it updated

Two things update, and they ship together from one tag so they always carry the same version number.

6.1  The app on your computer

~/.overwatch/bin/overwatch update

It reads a signed manifest from the release feed, checks the signature against a public key compiled into the program, downloads the archive for your platform, verifies its SHA-256, replaces itself and restarts the service.

6.2  The firmware on the board

Nothing to do. When the board says hello and its version is behind the feed, the daemon offers the update and the board shows a prompt. Tap it. The whole thing takes under a minute over the cable.

12:48:16 [bridge] ota: offering 2.1.0 (561659 bytes)
12:48:20 [bridge] <- {'t': 'ota_flash'}
12:48:23 [bridge] ota: flashing 2.1.0
12:49:09 [ota] update landed: wanted 2.1.0, running 2.1.0 (from 2.0.9)

A failed update is retried rather than abandoned, and the board asks again after two minutes. If a board is running a protocol this app does not speak, no update is offered at all — the daemon writes the slot in place with no test boot behind it, so "probably fine" is not a good enough basis for the one operation that can leave you holding a device that does not start.

After a self-update — fixed in 2.3.2

Older versions said "the background service is not running" immediately after update, and were wrong. Replacing the running binary invalidates its code signature and macOS kills the old process (last exit reason = OS_REASON_CODESIGNING); launchd restarts it, but the check gave up before it came back.

Not by a little. Measured on 30 September 2026: the bounce went out at 10:21:57, the check gave up at 10:22:02 after its five-second budget, and the new daemon's first log line is 10:22:08 — eleven seconds to start, because macOS has to assess the signature of a freshly written 12.8 MB bundle and its fifty-one inner Mach-O files before it will run any of them. A bounce of a binary already assessed answers in 0.02 s, so the wait is only ever spent when something is genuinely slow. The budget is now thirty seconds and prints a line so it does not read as a hang.

If you are updating from a version before 2.3.2 you will see the old message one last time, because the old code is the code running the bounce. Confirm with overwatch status and carry on.

7Uninstalling

~/.overwatch/bin/overwatch uninstall

Removes the login service, takes the status line and hooks back out of settings.json — restoring any status line of yours that was chained behind it — and leaves your own files alone.

It deliberately leaves Codex's trust records in ~/.codex/config.toml and says so, naming the file. Removing them looks tidier and is wrong: under codex exec a distrusted hook is skipped silently, with no prompt and no output, so a reinstall on a headless machine would produce a hook that is installed, correct, registered and permanently invisible.

Part II — What has been built

9From BLINK to Overwatch

Overwatch began as a fork of KfirLevy258/Blink and stopped being one.

Forty-eight commits separate it from upstream. The work falls into six strands, described in the sections that follow. The rebrand itself was a deliberate, complete separation rather than a change of name:

What movedFrom → to
Name and wordmarkBLINK → OVERWATCH, including the boot animation
State directory~/.blink/ → ~/.overwatch/, with a migration that runs once on a real machine
Release feedupstream's releases → this fork's
Signing keyupstream's public key → this fork's own keypair
Version linecontinued at 2.0.0 as its own product
Repositorymade public at SleepyUnicon/Overwatch

The migration was the delicate part. It renames the directory, then rewrites every string inside it that names the old one — the two markers that tell uninstall which hooks are ours, and the shims themselves. Renaming the files is not enough: the hook shim computes its own state directory as $HOME/.blink/$sub, so a shim that moved and was renamed still wrote where it always did. That recreated ~/.blink within a minute of the move, on the first hook that fired afterwards.

10Hardware bring-up

The board this project runs on is not the one the firmware was written for. A discrete ESP32 DevKitC and a standalone 2.8 inch module were wired on 13 jumpers and brought up on 23 September 2026 — screen, colours, touch, daemon, gauges.

Two findings were worth the trouble and are recorded in firmware/WIRED.md: the SDO wire that stops the board booting (§2.1), and touch arriving inverted on both axes after the panel change, fixed in the device-tree overlay by dropping invert-x and adding invert-y.

11The case

Two snap-fit designs, sized to the glass rather than the lit area, written in OpenSCAD and verified numerically rather than by eye — STLs were ray-cast and analysed for shell count and genus after every change.

That verification earned its keep. Six defects were found in geometry that looked correct in a render:

DefectCause
USB-C port sealed shutthe cavity used the spigot's width along its whole length; it now steps
All 21 vents sealedthe extrude began at 39 against a wall spanning 38–40
Port and aperture mirroredthe viewer's right is negative x — the whole front had to be unmirrored
Perch protruding 2 mmunclipped by the tray's inside profile
Corner relief through the wallonly 0.323 mm of material was available; the seat radius now comes from the clearance

The board's slot was also cut to the board — the ESP32 had been 1.6 mm short — and the spigot relieved where the display's connectors begin right at the edge.

12Firmware

12.1  Pages and theme

A page stack with cross navigation — gauges in the centre, music left, launcher right — plus settings, setup and sleep as overlays. Ten files used to carry their own #define COL_BG, which was survivable while they agreed and stopped being survivable the moment they did not: the gauges moved to white while the widget pages stayed near-black, so one swipe crossed from a white screen to a dark one. Colours now live in one palette structure with a light and a dark set.

12.2  The boot animation

The Overwatch wordmark, generated from the logo and encoded as BAN1 delta-RLE clips, replacing upstream's eye animation. The Codex edition gets its own variant with inverted ink. Frames are isolated by connected-component labelling so the mark is separated from its background cleanly.

12.3  The face

Two eyes and a mouth, drawn rather than played. The sleep screen used to play encoded clips of about 300 KB each, which is the right shape for one filmed animation and the wrong one for a face with moods: eight expressions times five gaze directions is not a clip library, it is a sprite sheet nobody can edit. The face is five rectangles and a table instead — an expression is a set of numbers and the tick eases toward whichever is current, so every expression blends into every other one for free, at a cost of a few hundred bytes.

12.4  The setup screen and QR

A brand-new board shows where to go, because it cannot send anyone there itself. The QR is drawn dark-on-light whatever the theme is doing — a code the theme made pretty and unscannable would fail in exactly the situation it exists for.

13The daemon and the web app

13.1  Extension without forking

The widget half is a subclass of the upstream bridge rather than an edit to it. Everything is additive, and unknown message types still fall through to the original handler, which ignores them exactly as before. That keeps upstream's releases from becoming merge conflicts.

13.2  The local page, and the security around it

The daemon serves a small page on 127.0.0.1:8730. Making it useful to a page hosted on GitHub Pages meant closing several holes at once:

  • Origin allowlist plus loopback, rather than a wildcard.
  • A pairing token in a header, compared with a constant-time comparison, stored at ~/.overwatch/pair.json with mode 0600.
  • Private Network Access headers, so a public page is permitted to reach a loopback service at all.
  • A CSRF hole closed — simple requests need no preflight, so the state-changing routes were made to require the token and the pairing route made same-origin only.

13.3  The setup site

A page on GitHub Pages that opens with the same animation the device plays, lays the steps out as tiles, and — once paired — mirrors the device's own UI so you can assign launcher tiles by clicking the picture of the thing on your desk. Phone detection is done in CSS rather than JavaScript, after innerWidth was measured reporting 1190 on a 375-pixel viewport.

16The most recent work, in detail

Three pieces of work completed 26–28 September 2026.

16.1  macOS signing and notarisation

The pipeline is written, wired into the release workflow, and dormant. With no certificate in the repository's secrets every step prints why the build is unsigned and exits successfully — which means the credential-free path is exercised on every push rather than discovered on the first release after somebody adds a certificate.

The finding that shaped it is worth stating plainly, because it would otherwise have surfaced at two in the morning after paying Apple:

The hardened runtime breaks a PyInstaller binary

Notarisation requires the hardened runtime. The hardened runtime enables library validation, which refuses to load any library whose Team ID differs from the process's own. Signing all 53 Mach-O files ad-hoc with --options runtime produces a binary that does not start at all:

Failed to load Python shared library '.../_internal/Python':
  ... not valid for use in process: mapping process and mapped
  file (non-platform) have different Team IDs

An ad-hoc signature carries no Team ID, so nothing can match anything. The hardened runtime is therefore set only on the Developer ID path, where all 53 files share one identity.

Because that last part cannot be rehearsed without a paid certificate, the signing script's final act is to run the binary it just signed and refuse to pass it on if it does not start — naming the entitlement escape hatch if the failure is that one.

Other details settled: the embedded Python.framework is signed as a bundle, not as the bare Mach-O inside it; every file is verified individually, because --deep says nothing about a one-directory build; and there is deliberately no stapling, since a ticket cannot attach to a loose executable or a tarball.

Enabling it needs six repository secrets and an Apple Developer membership. The steps are in docs/notarisation.md.

16.2  The Windows test suite

The installer workflow had been red on every push for weeks: 64 passing, two failing, and the Windows job's 17 failures had been read as path noise. Two of them were the product being broken on Windows.

CauseDetail
Migration did nothing
real bug		 The rewrite built its search strings from os.sep, so on Windows it looked for \.blink\blink-hook.sh. Every string it has to rewrite there is spelled with forward slashes — the shims are POSIX sh, and the commands in settings.json go through a helper that converts every backslash because a backslash is an escape under Git Bash. So a Windows migration moved the directory and left every reference inside it pointing at the old one, which the hook shim then recreated on the next tool call.
Mixed-separator path
real bug		 expanduser("~/.codex") replaces the tilde and leaves the slash alone, giving C:\Users\k/.codex. Windows opens it happily, so it went unnoticed — but it is not string-equal to the native spelling, so anything comparing or printing it disagreed with everything else, including the path shown to the user during uninstall.
Tests pinned to one platform
15 failures		 Seven hardcoded sh <shim> <event> where Windows deliberately emits bash; three set HOME but not USERPROFILE, so they wrote to one directory and read another; one used chmod(0o000), which on Windows only toggles read-only; one asserted behaviour that cannot exist there.

One of the seven had been passing on Windows while proving nothing: its "customer wrapper around our command" did not mention the command at all on that platform.

16.3  The firmware host tests — and a real regression

Three suites had been failing. All three were telling the truth.

What's New overran its page

Seven release-note lines were over the 33-character limit, up to 36. Past that the label wraps, and a wrapped line is a row the pagination arithmetic did not count, so the text overruns the page it was measured for.

Dark mode shipped the palette the test exists to forbid

The contrast suite kept its own copy of eight colours and grepped the view source to prove they still agreed. When the scattered colour defines were gathered into a theme file, those defines stopped containing values — so the grep matched nothing and reported all eight as drifted, which read as noise about a file move.

It was hiding this. Every WCAG rule had been running against the copy, and the copy was a set of values that by then existed nowhere. Meanwhile the real dark palette had been filled in from the widget pages, which had never had the severity ramp fixed. Dark mode was shipping:

band spread   2.30x   (amber 11.39:1 over red 4.95:1)   need <= 1.35
green sat     0.775   (the "green looks grey" fault)      need >= 0.85
red   sat     0.740

An inverted severity ramp — loudest at "getting close", quiet at "critical" — and a green that reads as grey at 60 cm. Both had already been fixed once on the gauge screen; gathering the palettes handed them back.

Fixed in 2.1.0

The dark ramp is restored to the measured trio: 1.16x spread, saturation 0.92 and up. The test keeps no copy — it parses both palettes out of the theme file and checks both, and an unreadable file is now a failure rather than a skip.

The layout test was two revisions behind a correct screen

Here the firmware was right every time. A dead constant the caption had stopped using; an arc position that moved deliberately and an assertion that did not follow; a percentage that is no longer centred alone because a unit line was stacked above it; and a hardcoded brand edge that was the left edge of a centred "BLINK", summed by hand from the font table, for a word that is now nine glyphs and sits at the right bezel.

Three numbers the screen depends on were prose rather than constants, which is how they went stale unseen. They are constants now, and the test reads them.

21Rules learned the hard way

Never use west flash on this board

It writes MCUboot into the application slot at 0x20000 and the screen goes dark. Flash with explicit esptool offsets instead: MCUboot at 0x1000, the application at 0x20000.

RuleWhy
Release notes: 33 characters, hard Beyond that the label wraps and the page overruns. Seven lines shipped over it because nothing was running the test that says so.
Zephyr 4.3.1, SDK 0.17.4 4.4.0 cannot build this firmware: its mbedTLS removed the header the OTA code includes, and its LVGL moved a field the settings screen reads.
Never expanduser("~/x/y") for a path you will compare It leaves the slashes alone and produces a mixed-separator path on Windows.
Redirect HOME and USERPROFILE Python reads the first on POSIX and the second on Windows.
A test that duplicates what it checks can be green about a broken product The contrast suite was, for weeks. Read the source; do not copy it.
A skip is not a statement about behaviour If a platform genuinely differs, assert the difference.
Code that has never run does not work A sealed port, sealed vents, a stuck setup screen, a dead retry and a WiFi build that would not link all reached the tree looking correct.
Try a different cable first Most "the board is gone" reports were one charge-only cable.
